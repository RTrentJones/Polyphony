# Polyphony — Deep review (October 2026)

**Scope**: the whole repository at `d8c2fc8` (PR #33 merged), read against the
[BRD](BRD.md), [ADR-002](ADR-002-book-as-root.md) and the five invariants in the
`polyphony-canon` skill. Backend, frontend, jobs, LLM layer, evals and CI were all read; the
unit suite was run locally (466 passed, 17 Postgres-only tests skipped).

**Output**: this document records what is true today. The work it implies is broken into
deliverable specs in [`docs/specs/`](specs/README.md), each of which cites the findings below by
number (F1, F2, …).

---

## 1. Summary

The book-as-root effort (July 2026, PRs #19–#32) landed most of what the BRD asked for. Book is
now the real parent of characters, sources, canon entries and style; `sanitize_for_llm` is gone
and `clean_for_llm` + spotlighting replaced it; `entity_versions` gives forward-only restore for
plans, characters, canon entries, style and synopsis; extraction proposes and the author commits;
the staged outline runs as a job with a deterministic principal-cast gate; and the job worker
pauses on quota instead of failing. The engineering quality of that work is high: the code
explains its own invariants, the tests are numerous and targeted, and the operational details
(woken worker, success-only health cache, Neon autosuspend) show real care.

The weak points are concentrated in three places.

The first is that **the invariants were enforced on the outline path and not carried to the
other generators.** Prose-mode scene generation, which is the default and the only mode the free
tier allows, receives none of the book's synopsis, canon entries or style guide and no injection
fence, and continuity checking still silently cuts its fact sheet to 4,000 characters. These are
the same class of defect that produced "Elara", in the two features an author uses most after the
outline.

The second is that **the evals no longer measure the product.** The staged outline returns a job
handle, extraction now waits for a reviewed commit, and the eval harness was not updated for
either, so the API-mode outline, extraction and ingestion steps can only score zero, and the
`cast_fidelity ≥ 0.9` CI gate the BRD names as its acceptance test was never wired. A regression
in fidelity would currently ship green.

The third is that **the free-tier promises are weaker than the BRD claims.** The circuit breaker
counts quota exhaustion as failure, so a sustained 429 eventually turns pauses into dead jobs;
the paid "config flip" changes neither the pacing rate nor the token cap; and pauses are visible
only for scenes.

Beyond those, the product surface has gaps an author would notice quickly: scene casting is
free-text names chosen from the wrong list, the outline's structured cast and restated premise
are discarded before the author sees them, the G4 visibility features (voice-chunk browser,
retrieval inspector) exist only as API endpoints, and extraction is a single call that cannot
handle a real manuscript.

None of this calls for redesign. The architecture (one container, one Postgres, durable jobs,
provider-fungible client, `Canon` as the assembly point) is the right shape, and nearly every fix
below is a matter of routing an existing mechanism through a path that currently bypasses it.

## 2. What is solid and should be preserved

- **`app/planning/canon.py`** is the right abstraction. `Canon.full_block()` assembles the whole
  canon, fences it, and raises on overflow. Every generator should consume it (F1, F2).
- **`app/core/llm_text.py`** implements ADR-002 §4 faithfully; the module docstring is the best
  statement of the threat model in the repo.
- **The job system** (`app/jobs/`) is well built: atomic enqueue with the domain row, `FOR UPDATE
  SKIP LOCKED` claiming, after-commit wake, deadline-based idle, boot reaping, `on_dead` and
  `on_pause` hooks. Specs below extend it rather than replace it.
- **Extraction commit** (`app/api/extraction.py:167`) is careful: row-locked exactly-once commit,
  merge-by-name honouring `model_fields_set`, explicit `skipped`, M2M provenance.
- **Versioning** (`app/versioning/`, `app/api/versioning.py`) is append-only with forward-only
  restore, re-validates old content on restore, and can recreate a deleted entity.
- **Operational care**: `/health` vs `/health/live`, success-only health caching, the worker that
  issues zero queries when idle, route-template metric labels, validation-error redaction.
- **Tests**: 466 unit tests plus a pgvector integration job in CI, and frontend type-check, lint
  and build in CI.

## 3. Findings

Severity: **P0** breaks a BRD invariant or a stated guarantee; **P1** is a significant product or
reliability gap; **P2** is hygiene. Line numbers are at `d8c2fc8`.

### P0 — invariant and guarantee violations

**F1. Prose-mode scene generation is canon-blind and unfenced.**
`write_beat_prose` (`app/orchestration/prose.py:32`) builds its prompt from the request's
`setting`, `emotional_tone`, free-text `style_notes`, the chapter summary and per-character
context. The book's synopsis, canon entries and style guide (POV, tense, tone, sample prose) never
reach it, so a book whose style guide says "first person, present tense" gets whatever the request
form said, and a scene set in Aeon Holdings knows nothing about Aeon Holdings. The beat planner
(`app/orchestration/workflow.py:18`) is likewise canon-free. Neither prompt uses
`STORY_MATERIAL_NOTICE` or `as_quoted_block`, although voice samples come from uploaded files,
which ADR-002 §4 classifies as untrusted. This is R1.1 ("every generation") and R2.3 broken on
the default and free-tier-only scene path. The ensemble path does use `Canon.full_block()`, so
the two modes are inconsistent.

**F2. Continuity silently truncates and under-feeds its fact sheet.**
`check_chunk` interpolates `{fact_sheet[:4000]}` (`app/planning/continuity.py:61`), the exact
silent-cap pattern invariant 1 forbids; with a 20k-character synopsis at the head of the fact
sheet, the cast and every chapter summary are cut. `_build_fact_sheet`
(`app/api/plans.py:521`) renders characters as one line (role, description, goals), omitting
arc, relationships, traits, voice, canon entries and the style guide, instead of using
`render_bible`. The prose is not fenced. A JSON parse failure returns `[]`
(`continuity.py:87`), which is indistinguishable from "no contradictions", so the UI can report a
clean check that never happened (eval backlog item 7, still open).

**F3. The circuit breaker turns quota pauses into failures.**
`LLMClient` constructs its breaker with `expected_exception=Exception`
(`app/llm/client.py:71`), so every `QuotaExhaustedError` counts toward `failure_threshold=4`.
After four quota-paused calls (which on a shared free-tier key is the normal shape of quota
exhaustion), the breaker opens and the next call raises `CircuitBreakerError`. The worker catches
only `QuotaExhaustedError` (`app/jobs/worker.py:230`), so that job is marked failed and, with
`max_attempts=1` on scenes and outlines, goes dead. Invariant 5 ("free tier never loses work")
does not hold under sustained quota exhaustion. The breaker is also process-global, so one user's
quota storm blocks every other user's calls for the recovery window.

**F4. The paid "config flip" does not raise rate limits or caps.**
`Tier.max_rpm` is read by nothing; the pacer uses `LLM_MAX_RPM or provider.max_rpm`
(`app/llm/pacing.py:49`). `get_tier()` overwrites `daily_token_limit` with
`USER_DAILY_TOKEN_LIMIT` (`app/llm/tier.py:70`), so `PAID.daily_token_limit = 5_000_000` never
applies, and `budget.py` reads the setting directly anyway. `MONTHLY_COST_CEILING_USD` is
surfaced by `/usage` and enforced nowhere. Graduating today requires setting `LLM_TIER`,
`LLM_MAX_RPM` and `USER_DAILY_TOKEN_LIMIT` together, which contradicts R7.6. Separately, nothing
models the provider's requests-per-day ceiling, which BRD §6.1 identifies as the probable binding
limit.

**F5. The eval harness no longer exercises the product, and the fidelity gate does not exist.**
- The API outline step calls `POST /plans/generate` and reads `content` from the response
  (`evals/steps/pipeline.py:167`, `evals/harness/client.py`). Since Phase 5 that endpoint returns
  `{plan_id, job_id, status: "generating"}`, so `nodes` is always empty and the step scores 0.
  The eval book is also created with no characters, so even a working poll would gate on an
  empty principal set (recall trivially 1.0).
- The API extraction and ingestion steps upload and immediately read
  `/sources/{id}/characters` (`pipeline.py:36`, `:58`). Since Phase 6 characters exist only after
  a reviewed commit, which the harness never performs, so both steps score 0.
- The offline extraction step grades the legacy `CharacterExtractor` (`evals/offline.py:79`),
  which the product no longer uses for canon; production extraction is
  `app/parsing/canon_extractor.extract_canon`.
- `cast_fidelity` is computed only in `evals/offline.py:135`. `evals.yml` grades `dracula` and
  `frankenstein` by default and never the `cel` corpus, and nothing fails CI on fidelity. The
  BRD §7 acceptance gate is unimplemented.

**F6. Scenes are not book-rooted.**
`Scene` has no `book_id`; it reaches a book only through `chapter_id`, which is nullable with
`ON DELETE SET NULL` (`app/core/orm_models.py:374`), and the `Chapter.scenes` relationship has no
delete cascade. Deleting a chapter or a book therefore leaves its scenes, beats and revisions as
user-scoped orphans that no book-scoped view can reach, while `GET /api/v1/scenes/` still lists
them. `list_book_scenes` (`app/api/books.py:465`) papers over this with an OR across chapter and
source. This contradicts invariant 2 and BRD §4.1, where Scene sits under Chapter under Book.

**F7. Rate limiting is almost certainly keyed on the tunnel, not the user.**
Both limiters use `get_remote_address` (`app/main.py:128`, `app/api/auth.py:36`) and uvicorn runs
without proxy-header trust (`Dockerfile` CMD). Behind `cloudflared` every request arrives from the
tunnel's address, so `login` at 5/minute and `register` at 3/hour are global: one script can lock
every user out of login, and the 60/minute default is shared by all authenticated users, whose
polling UIs (scenes and plans poll while jobs run) count against it. This should be confirmed in
production logs before the fix ships, but the code admits no other reading.

### P1 — significant product and reliability gaps

**F8. Extraction cannot handle a real manuscript.**
`extract_canon` sends the whole source in one call, bounded only by `MAX_SOURCE_CHARS = 2,000,000`
(~500k tokens), with `max_tokens=4096` for the answer (`app/parsing/canon_extractor.py:71`). A
90k-word novel is roughly 120k input tokens, which is over half of a user's daily budget, with no
preflight; and a real cast plus world does not fit in 4,096 output tokens, so the JSON truncates,
parsing fails, the job retries once (`max_attempts=2`) and spends the same tokens again.
Proposals carry only name, role and description for characters, so goals, arc, relationships,
voice and aliases are never proposed. `cat in _CATEGORIES` (`:53`) is a substring test against a
string, so categories like `"on"` or `"loc"` pass validation and are stored. The narrator-voice
and HTML-paragraph problems from the audit backlog (items 1 and 2) are still open.

**F9. The staged outline throws away what the author most needs to see.**
`premise_restated` and `central_conflict` (`app/planning/staged_outline.py:41`) exist so that a
misreading is caught at stage one (R1.3), but they are used only as context for later stages and
never persisted or shown, so the author cannot catch the misreading. The chapter stage's
structured `pov`, `characters`, `act_index` and `threads` are dropped because the beat stage does
not ask for them back and `validate_outline_nodes` (`app/planning/outline.py:23`) keeps only
`title`, `summary` and `children`. Promoting a node to a chapter (`app/api/plans.py:296`)
therefore carries no cast or POV, is not idempotent (promoting twice duplicates the chapter) and
does not record which node a chapter came from.

**F10. Scene casting is free text chosen from the wrong list.**
`ChapterSceneRequest.characters` is `list[str]` (`app/api/books.py:84`). The generate modal
offers characters from a *source* picker populated by `fetchSources()` with no `bookId`
(`frontend/app/books/detail/page.tsx:166`), which lists the user's sources across all books, plus
a comma-separated text box. A name that does not exactly match a character in this book is
rendered as "(No bible entry — infer a consistent voice.)" (`app/characters/context.py:89`) with
no warning, so a typo or a character from another book silently produces voice-blind prose.
`parse_beats` assigns the full cast to every beat (audit backlog item 5).

**F11. Pauses are invisible outside scenes, unbounded, and uncancellable.**
Only the scene handlers register `on_pause` (`app/jobs/handlers.py:272`). A paused outline stays
`generating`, a paused extraction stays `pending`, and a paused continuity report stays
`processing`, so the UI cannot tell "waiting for quota" from "stuck". A job pauses indefinitely
(`repository.pause` decrements `attempts`), so a daily-quota outage re-pauses every 15 minutes
forever. There is no cancel endpoint for any job kind.

**F12. Resume restarts multi-call work from scratch.**
BRD R7.2 states that a scene is a single-call job and resumes without duplicate spend. A prose
scene is `1 + N` calls (planner plus one per beat) and an ensemble scene is far more; on resume
the workflow restarts at the planner and re-spends every completed beat. `SceneBeat` rows already
exist but are written only on success (`prose.py:153`), so checkpointing is close at hand. The
staged outline has the same limitation, which the BRD does acknowledge.

**F13. LLM calls still run inside HTTP requests.**
The single-call outline fallback (`app/api/plans.py:265`) and `test-dialogue`
(`app/api/characters.py:326`) call the model synchronously. With four attempts and up to 120 s of
backoff per 429, a single request can exceed Cloudflare's 100 s origin timeout and surface as a
524 while the work continues server-side. `test-dialogue` also skips `check_user_budget`.

**F14. No idempotency guard on expensive enqueues.**
`generate_plan` enqueues a new staged job even when the plan is already `generating`;
`reprocess_source` and `edit_source` start a new extraction run while one is pending; a
double-clicked "Generate scene" creates two scenes. Each duplicate re-spends quota.

**F15. G4 visibility exists in the API but not in the product.**
The voice-chunk browser and editor, retrieval inspector, voice-sample seeding and test-dialogue
endpoints (`app/api/characters.py:283`–`:424`) have no frontend callers; their TypeScript types
exist in `lib/types.ts` and nothing renders them. The ensemble mode cannot be selected in the
UI. `/usage` has no page. R7.5 (show cost before an expensive action) is not implemented anywhere.
R5.3's second half (which chunks grounded *a specific generation*) is not recorded: scenes store
no retrieval provenance.

**F16. "Nothing is destroyed" has holes.**
Source content edits overwrite `content_text` in place (`app/api/sources.py:239`) without a
version, although the feature set lists `source` as a versioned type. Chapter title and summary
edits are unversioned, and promote-generated summaries can be overwritten without trace.
Deleting a character removes its voice chunks first (`characters.py:277`); restore can recreate
the row but not the voice. Deleted entities can be restored only by someone who already knows
their ID, because nothing lists them.

**F17. The ensemble diverges from its own spec.**
R6.2 (action grounding retrieved separately from dialogue) is not implemented; proposals use the
same mixed retrieval as prose. `chapter_summary` is accepted by `run_ensemble_scene_workflow` and
never used. The narrator receives `clean_for_llm(prior_tail)[:600]` (`ensemble.py:143`), a silent
cut. There is no preflight or cost estimate, and when the tier forbids ensemble the request is
silently downgraded to prose (`books.py:600`) with nothing in the response saying so.

**F18. `character_chunks` is a write-only mirror that drifts.**
`add_voice_samples` writes both `voice_chunks` and `CharacterChunk` (`characters.py:310`), but
chunk edit and delete touch only `voice_chunks`, and nothing reads `character_chunks`. The
feature set already flagged this for reconcile-or-drop.

### P2 — hygiene

**F19. The catalogue is stale.** `docs/feature-set.md` still marks most book-as-root work ⬜
(book_id NOT NULL, Source, versioning, staged outline, tiering) although it shipped in PRs
#19–#32, and the eval-audit backlog does not record which items closed. The skill tells agents to
read these first, so stale status actively misleads.

**F20. Smaller defects.**
- `add_thread_event` (`plans.py:488`) does not check that `scene_id` belongs to the user, nor
  that `chapter_id` belongs to the thread's book.
- Export includes the book's synopsis (the author's storyboard) in the manuscript output by
  default (`books.py:850`).
- `app/migrate.py`'s legacy-reset shim says to delete itself once past the transition.
- `"1.0.0"` is hard-coded in several places in `app/main.py`.
- `frontend/app/books/detail/page.tsx` is 2,258 lines holding seven panels and a modal, and there
  are no frontend unit tests.
- `delete_character` deletes vectors in one session before the row delete commits in another; a
  failed commit leaves a character with no voice.

## 5. Recommended order

The specs are sequenced so that the evals can see a change before the change lands, and so that
the invariant fixes come before new surface area. See [`specs/README.md`](specs/README.md) for
the dependency graph and sizing.

1. **Make the evals see the product** (SPEC-06) — otherwise nothing after it can be measured.
2. **Honour the invariants everywhere** (SPEC-01, -02, -03, -04, -05) — the P0 set.
3. **Jobs that never lose work, visibly** (SPEC-07, -08).
4. **Extraction for real manuscripts** (SPEC-09) and **the outline → chapter → scene handoff**
   (SPEC-10) — the two largest author-facing gaps.
5. **Visibility and control in the UI** (SPEC-11, -12, -13).
6. **Ensemble v2** (SPEC-14), gated on the requests-per-day decision.
7. **Hygiene** (SPEC-15) can run in parallel throughout.
